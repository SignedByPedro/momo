# Momo v2.20: persistent login QA

This version changes only session maintenance in the existing Admin and Client Portal. No migration, new secrets or Supabase Auth setting changes are required.

## Before deploy

Run from the project root:

```powershell
node scripts/test-v220-session.mjs
node scripts/test-v217-conversation.mjs
npm run lint
npx tsc --noEmit
npm run build
```

The deterministic script tests check configuration and wiring. They **cannot** verify a live Supabase session. If local dependencies are already installed you may omit `npm ci`.

## Manual tests after deployment

Use the same normal browser profile (not a private browsing window):

1. Sign in at `/admin/login`, refresh `/admin` several times and duplicate the Admin tab. Both tabs should stay signed in. Navigate between protected Admin pages.
2. Leave an Admin tab open until it has been idle longer than the configured JWT expiry and return to it. Refresh and navigate again. Session renewal should work if the Supabase session has not been revoked or expired by server policy.
3. Click **Sair**. Refresh the Admin tab and open a new Admin tab. Protected pages must redirect to the Admin login screen.
4. Repeat tests 1-3 for `/portal/login`, including opening Portal Support after refresh.
5. Verify that a user without Admin membership cannot access `/admin` and a user without accepted Portal membership cannot access `/portal`.
6. Check an invitation acceptance and password setup when a new test account is available.

**Important:** Admin and Portal use the same Supabase project and therefore share one authentication cookie in a browser profile. You cannot stay logged in simultaneously as two *different* accounts in two tabs of that same profile. Use separate browser profiles when testing distinct Admin and Portal accounts. A private window has its own cookie storage, and a browser set to erase cookies on exit will not remember the login.

If a valid session is still unexpectedly lost, do **not** extend JWT lifetimes or disable authorization checks as a workaround. Check browser cookie retention (same origin/path), the browser console and Supabase Auth session policies, then reproduce with the actual failed URL and timing. Never copy access or refresh tokens into troubleshooting reports.

For production: `npm run build` followed by `npx vercel --prod` after the checks pass.
